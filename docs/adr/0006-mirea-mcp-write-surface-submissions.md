# 0006: Поверхность записи mirea-mcp — ответы на работы СДО; разделение «поиск/исполнение», OIDC-only, no-cobber, подтверждаемая отправка

**Status**: accepted (реализовано и live-проверено на полигоне `id=952087` 2026-11-22; дизайн выдержал контакт с Moodle, механика уточнена ниже)

## Контекст

mirea-mcp до этой точки был read-only. Запрошенные инструменты записи (прикрепление, замена, переименование, удаление вложений, отправка ответа) нацелены только на ответы на работы (`mod/assign`, файловый submission-плагин) — форумы и прочие виды активности сознательно вне scope: пользователь их не использует, а каждый вид активности — отдельный workflow с собственной моделью необратимости. Операции идут против живой учебной среды, где отправка ответа преподавателю необратима без его согласия, а черновик (вложения до отправки) преподавателю не виден. Отдельное ограничение: `sesskey` существует только в браузерной OIDC-сессии (ADR-0004/0005), поэтому запись через dormant REST-режим (`MIREA_SDO_TOKEN`) структурно невозможна.

## Решение

Десять инструментов: `submit_find` (режимы `url` — точный, и `query` — нечёткий с расшифровкой аббревиатур по глоссарию; верхние 5 кандидатов с `matched_terms`; **нечёткий поиск никогда не исполняет действие, даже при единственном совпадении**), `submit_attach` (no-cobber: совпадение имени файла — ошибка, а не «файл (1).pdf»), `submit_bulk_attach` (список путей или каталог), `submit_replace` (атомарная замена содержимого через нативный action filemanager), `submit_rename` / `submit_bulk_rename`, `submit_remove` / `submit_bulk_remove`, `submit_all_remove` (wipe только явным флагом), `submit_post` (`confirm=False` по умолчанию — dry-run превью: вложения, дедлайн, статус; отправка только при `confirm=True`), `discipline_abbreviations` (чистая функция «первая буква каждого слова без пунктуации», unit-тесты; мемо в `.cache/abbreviations.json` с проверкой хэша источника — staleness невозможна; перезаписи логируются в `.logs/YYYY-MM-DD.log`). Все action-инструменты принимают **только `url`** и под капотом проходят точную валидацию (это assign с файловым плагином, ответ редактируем) — free-text запрос физически не достигает кода, мутирующего состояние. Запись — только в OIDC-режиме; каждая мутация перевытаскивает `sesskey`, переживает умершую SSO-сессию с `SdoAuthError` и подсказкой на `mirea_auth_start` (ADR-0004). Результат каждой мутации — повторно считанный с страницы **наблюдаемый** список вложений, а не «ok».

**Considered Options**: единый монолитный `submit(work, files)` — отвергнут: прячет необратимую отправку внутри бытовой загрузки; fuzzy-поиск внутри action-инструментов — отвергнут: превращает угадайку в запись; replace как `remove`+`attach` — отвергнут: окно «файл удалён, новый не доехал»; TTL-кэш аббревиатур — отвергнут в пользу мемо с хэшем источника (инвалидация не нужна); bulk-инструменты, принимающие смешанные списки — отвергнут: единичные операции остаются единичными, чтобы опечатка удалила один файл, а не половину списка.

**Consequences**: тестирование мутаций возможно только против живой СДО — принят полигон `/mod/assign/view.php?id=952087` (лаб. 4 ПЭПИС) с обязательной зачисткой вложений после прогона; `submit_post` дополнительно live-тестируется реальной отправкой с согласия пользователя. Термины «ответ на работу», «вложение», «черновик», «отправка» закреплены в `GLOSSARY.md`. Имена инструментов английские, описания русские (ADR-0001).

## Механика Moodle после реализации (live-верификация, 2026-11-22)

Факты, которые гриль-сессия предсказать не могла — зафиксированы, чтобы следующий не гадал:

- **Черновики ответов на online-edu отключены**: единственная кнопка формы «Сохранить» == отправка преподавателю. Поэтому мутации стадируют изменения в черновую файловую область (`draftfile.php`, itemid из формы `editsubmission`), а публикует только `submit_post` (`files_filemanager=<itemid>` в POST `view.php` с hidden-полями формы). Стадировка живёт в памяти процесса MCP-сервера.
- **Moodle перевыпускает `itemid` при каждом открытии `action=editsubmission`** — загрузка в протухший itemid молча теряется. Клиент пинит draft-контекст по cmid до успешной отправки; `resolve`/`reload` пин не сбрасывают. При ответе Moodle о невалидном sesskey пин перевыпускается один раз с повтором операции.
- **`draftfiles_ajax.php?action=deleteselected`** принимает `selected` как JSON-массив **объектов** `[{"filepath": "/", "filename": "…"}]` (plain names → `get_filepath() on null` на стороне Moodle; формат взят из YUI `/lib/form/filemanager.js`).
- **`repository_ajax.php?action=overwrite`** (атомарный replace) возвращает голый JSON `true`/`false`, не dict.
- **Каждая страница Moodle несёт `<noscript><div class="alert-danger">JavaScript отключен…`** — проверка успеха отправки обязана игнорировать alert-ы внутри `<noscript>`, иначе каждая отправка «падает» после фактического успеха.
- **Пустую отправку Moodle отклоняет** («Ничего не было представлено»): сохранённый ответ нельзя опустошить до нуля инструментами — нижний предел один файл, последний снимается вручную.
- **Аббревиатуры**: имена дисциплин в СДО декорированы (`Базовое имя_Зачет (часть N/M) [I.xx-yy]`) — derive() работает по части до первого `_`; кэш-мемо хранит `source_hash` + `ALGO_VERSION` (смена алгоритма = авто-рефреш, без TTL).
- Аббревиатура пользователя «ПЭПИС» совпала с производной «первая буква каждого слова» от «Программирование электронных приборов и систем» — правило подтверждено эмпирически.

## Ревизии

**2026-11-22 (второй заход)** — два уточнения по итогам боевого использования:

- **Пин черновика стал двухуровневым.** Первоначально контекст черновика жил только в памяти процесса MCP-сервера: attach в одном процессе + `submit_post` в другом молча теряли стадировку («Ничего не было представлено» — воспроизведено на полигоне `id=943014`). Пин теперь дополнительно персистится в `draft.json` (каталог состояния, 0600) и сбрасывается с диска только после успешной отправки. Рестарт сервера между attach и post безопасен.
- **Нечёткий поиск упрощён: ранжирование удалено.** Реальный кейс «ЛР4» давал обе лабораторные (3-4 (2) и 7-8 (4)) с равным score — ранжирование не помогало выбрать, а сложность мешала тестировать. Поиск теперь простой фильтр: все токены обязаны совпасть (raw/тип работы/аббревиатура дисциплины), результат — ВСЕ совпадения в алфавитном порядке (дисциплина, работа); поля `score`/`matched_terms` и параметр `limit` удалены.
