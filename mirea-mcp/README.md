# mirea-mcp

MCP-сервер, дающий агентам доступ к данным РТУ МИРЭА: дисциплины, баллы (СДО),
посещаемость, расписание (Пульс) и план «что сдать / что посетить»,
построенный по правилам БРС из `brs-semester.json`. С ADR-0006
добавлена поверхность записи: сдача работ СДО (вложения, отправка ответа).

Термины — в `docs/GLOSSARY.md` (Дисциплина, Баллы, СБ, БП и т.д.).
Источники данных — ADR-0002, baseline плана — ADR-0003, аутентификация — ADR-0004.

## Установка

```bash
cd mirea-mcp
uv sync
cp .env.example .env
```

Заполнить в `.env`:

- `MIREA_LOGIN` / `MIREA_PASSWORD` — SSO-аккаунт `@edu.mirea.ru`.

## Запуск и регистрация

Пример записи в `.omp/mcp.json` (формат oh-my-pi mcp-schema):

```json
{
  "mirea": {
    "type": "stdio",
    "command": "uv",
    "args": ["run", "--project", "/абсолютный/путь/mirea-mcp", "mirea-mcp"],
    "timeout": 30000
  }
}
```

Важно: MCP-серверы монтируются при старте сессии omp. После правки конфига
нужна новая сессия, запущенная из корня репозитория.

## Инструменты записи (сдача работ, ADR-0006)

Операции над ответом на работу (`mod/assign`, файловый submission-плагин).
Имена английские, описания русские (ADR-0001).

- `mirea_submit_find(url)` — точный режим: валидация страницы работы
  (это assign с файловым плагином, ответ редактируем). Возвращает цель
  сдачи (cmid, статус, дедлайн, вложения). `mirea_submit_find(query)` —
  нечёткий режим: расшифровка аббревиатур по глоссарию, все совпадения
  в алфавитном порядке (без ранжирования); **нечёткий поиск никогда не исполняет
  действие, даже при единственном совпадении** — результат нужно явно
  передать в `url`.
- `mirea_submit_attach(url, path)` — прикрепить файл к черновику;
  no-cobber: совпадение имени файла — ошибка, а не «файл (1).pdf».
  Результат — наблюдаемый список вложений, перечитанный со страницы.
- `mirea_submit_bulk_attach(url, paths | directory)` — то же для
  нескольких файлов: списком путей или целым каталогом; no-cobber
  действует на каждый файл.
- `mirea_submit_replace(url, filename, path)` — атомарная замена
  содержимого вложения через нативный action filemanager (не
  «удалить + прикрепить», нет окна «файл удалён, новый не доехал»).
- `mirea_submit_rename(url, filename, new_name)` /
  `mirea_submit_bulk_rename(url, renames)` — переименование одного или
  нескольких вложений; в bulk-режиме переименования — явный словарь
  «старое имя → новое».
- `mirea_submit_remove(url, filename)` /
  `mirea_submit_bulk_remove(url, filenames)` — удаление одного или
  нескольких вложений; единичные операции остаются единичными, чтобы
  опечатка удалила один файл, а не половину списка.
- `mirea_submit_all_remove(url)` — удаление всех вложений черновика;
  wipe — отдельный инструмент, чтобы опечатка в имени не стёрла ответ.
- `mirea_submit_post(url, confirm=False)` — `confirm=False` (умолчание):
  dry-run превью — сохранённые и застадированные вложения, дедлайн, статус,
  **без отправки**. `confirm=True` — отправка ответа преподавателю;
  необратима без его согласия (см. «Отправка» в GLOSSARY.md).
- `mirea_discipline_abbreviations(refresh=False)` — чистая функция
  «первая буква каждого слова без пунктуации» поверх базовых имён дисциплин
  (служебные суффиксы СДО вида `_Зачет (часть 1/2) [I.26-27]` отбрасываются);
  мемо в `.cache/abbreviations.json` с проверкой хэша источника и версии
  алгоритма (staleness невозможна), перезаписи логируются в
  `.logs/YYYY-MM-DD.log`; `refresh=True` — принудительный пересчёт.

### Безопасность записи

- Запись работает **только в OIDC-режиме**: REST через `MIREA_SDO_TOKEN`
  — read-only, мутации структурно невозможны (`sesskey` есть только в
  браузерной OIDC-сессии, ADR-0004/0005).
- Перед каждой мутацией выполняется auth-проверка: `sesskey`
  перевытаскивается заново; умершая SSO-сессия — ошибка `SdoAuthError`
  с подсказкой на `mirea_auth_start`.
- Все action-инструменты принимают **только `url`** и под капотом
  проходят точную валидацию страницы: free-text запрос физически не
  достигает кода, мутирующего состояние.
- **Модель стадинга**: на online-edu.mirea.ru черновики ответов выключены,
  поэтому «сохранить» == «отправить преподавателю». Мутации (attach/rename/
  remove/replace) изменяют только черновую файловую область Moodle и
  видны преподавателю исключительно через `submit_post`. Пин черновика
  двухуровневый: память процесса + `draft.json` в каталоге состояния
  (Moodle перевыпускает `itemid` при каждом открытии формы — пин держит
  один itemid до отправки). Рестарт MCP-сервера пин не теряет: файл,
  прикреплённый в одном процессе, уйдёт в отправке из другого; после
  успешной `submit_post` пин сбрасывается.
- Результат каждой мутации — **наблюдаемое** состояние: `attachments`
  (сохранённые, перечитанные со страницы) и `staged` (черновая область,
  то что уйдёт преподавателю при `submit_post`).
- Платформенный предел: Moodle отклоняет отправку **без единого файла**
  («Ничего не было представлено») — полностью опустошить сохранённый ответ
  инструментами нельзя, последний файл снимается вручную в интерфейсе СДО.

## Флоу первого входа

1. `mirea_status` — проверить, что сервер жив и конфиг читается.
2. `mirea_auth_start` — начать SSO-вход в Пульс.
3. Код приходит на корпоративную почту `@edu.mirea.ru`.
4. `mirea_auth_otp(код)` — завершить вход.
5. `mirea_plan` — получить план по БРС.

СДО-часть (`mirea_grades`, `mirea_due_works`, `mirea_disciplines`) работает сразу
после заполнения `.env`. Пульс (`mirea_attendance`, `mirea_schedule`, `mirea_plan`)
требует одного OTP-входа; состояние сессии сохраняется на диск.

## Обновление brs-semester.json

При выходе нового Положения о БРС:

1. Сверить параметры с `docs/normative-acts/CHANGELOG.md`
   (текущее: СМКО 8.5.1/03.П.72-26, БМАКС = 130 для 3 курса).
2. Обновить в `brs-semester.json` поля `bmax`, `categories`, `grade_scale`.
3. Тип контроля дисциплины (экзамен / зачёт) — в поле `disciplines`.

## Ограничения

- Write-инструменты СДО ограничены ответами на работы (ADR-0006); форумы
  и прочие виды активности вне scope сервера.
- ЛКС вне scope сервера (см. ADR-0002).
- `pulse.mirea.ru` блокирует IP датацентров — запускать сервер с локальной
  машины, не с сервера/CI.
- MCP никогда не отправляет пароль в Moodle (локальная auth отключена вузом и
  ведёт к блокировке аккаунта); вход в СДО — OIDC на SSO-сессии Пульса.
