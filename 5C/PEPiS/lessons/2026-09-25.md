# Lessons — 2026-09-25

Session: building the GOST-formatted report `pr1-2/pr1/report-pr1.docx` (practice work № 1,
STM32F1 I/O schematic, variant 4).

## Outcome

Report was first built with **docx-mcp** (markdown → styles patch → images/TOC/footer),
produced a package that **Word refused to open**, and was ultimately rebuilt with
**python-docx** (`pr1-2/pr1/generate_report.py`). That version opens cleanly in Word.

---

## Issues and workarounds

### 1. docx-mcp: markdown eats `[[PLACEHOLDER]]` markers
- **Problem:** `create_from_markdown` interprets `[[IMG1]]`-style lines as reference links;
  they disappear or get mangled.
- **Workaround:** Use plain unique marker tokens and locate them afterwards with
  `search_text` (regex), then insert content at those positions and delete the markers.
  Remember regex character classes: `[A-Z]+` silently misses digits (`IMG1`).

### 2. docx-mcp: some tools ignore `document_handle`
- **Problem:** `set_page_size`, `set_page_margins`, `set_document_language` operate only on
  the `__default__` session. Opening the doc under a named handle made these fail with
  "No document is open for handle '__default__'".
- **Workaround:** Close the named session, reopen the file into the default slot, then run
  those tools.

### 3. docx-mcp: footer cannot be created through normal tools
- **Problem:** The template has no footer part. `edit_header_footer` errors with
  "No footer found in document"; `bates_number` claims success but materializes nothing;
  `add_field` inserts fields only in the body.
- **Workaround:** `write_part("word/footer1.xml", xml)` **can create a new part** (verify with
  `read_part` — `list_parts` did not reflect it). Then wire it up:
  footer part → rel in `word/_rels/document.xml.rels` → `<w:footerReference>` as **first
  child of `<w:sectPr>`** → override in `[Content_Types].xml`.

### 4. docx-mcp save-time repair strips "broken" relationships
- **Problem:** On `save_document`, a repair pass removes relationships not referenced from
  `document.xml`. It removed the freshly added footer rel (footerReference wasn't in
  `document.xml` yet) — `broken_rels_removed: 1`.
- **Workaround:** Post-save zip surgery with stdlib `zipfile` (see `tools/patch_footer.py`):
  rewrite `word/document.xml` (insert `footerReference`) and the rels inside the zip.
  Note: the script's asserts make it idempotent. A later save from a session that *was
  opened from the patched file* kept the rel (`broken_rels_removed: 0`) — order matters.

### 5. `update_fields` tool silently does nothing
- **Problem:** `update_fields` returned `updated_count: 1`, but `word/settings.xml` stayed
  empty — no `w:updateFields` persisted, so Word would never refresh the TOC field.
- **Workaround:** Set the flag explicitly in python-docx
  (`settings.element.append(w:updateFields val=true)`). Verify by reading the part.

### 6. THE BIG ONE: docx-mcp package was corrupt for Word
- **Problem:** Word: *"Word experienced an error trying to open the file."* Yet:
  - `unzip -t` — OK;
  - every XML part well-formed (ElementTree);
  - python-docx opened and round-tripped it;
  - macOS `textutil` converted it fine.
- **Likely culprit:** the markdown-converted table was missing `<w:tblGrid>` and carried
  `w14:paraId` on `<w:tr>` — technically tolerated by Cocoa/LibreOffice, fatal for Word's
  stricter parser. Non-standard part serialization (parts without XML declarations) may
  also have contributed. Could not pin down 100 % without Word's validator.
- **Failed fix:** python-docx round-trip (preserves the invalid XML as-is).
- **Working fix:** regenerate the whole document with python-docx from scratch
  (`generate_report.py`). python-docx's canonical structures (table via `add_table`
  includes `tblGrid` automatically) are proven Word-compatible.

### 7. Don't trust non-Word validators for Word-targeted files
- Cocoa (`textutil`), python-docx, ElementTree all accepted the corrupt file. Only Word
  complained. **Test with the real consumer early** — ideally keep a minimal Word-safe
  baseline file and iterate on it.

## Process miscellany

- **Permission rules quirk:** `rm -f` and `rm -rf` are denied, plain `rm` is allowed.
- **LibreOffice install** (for PDF preview via `convert_to_pdf`) was started via
  `brew install --cask libreoffice` on Intel macOS (unsupported platform warning), never
  completed; user chose to skip. PDF preview remains unavailable — verify in Word instead.
- **venv:** python deps (python-docx, cairosvg) live in repo-root `.venv-report`.
  The "unresolved import docx" LSP errors in `generate_report.py` are just the IDE not
  knowing the venv — the script runs fine with `.venv-report/bin/python`.
- **tools/patch_footer.py** is now obsolete (the python-docx generator wires the footer
  natively) but kept for reference.
- KiCad schematic → PNG rendering (via kicad MCP export + region crop) worked well;
  annotate footnote areas were intentionally cropped out.

## Recommended workflow for future reports

1. Write/extend the python-docx generator (`*/generate_report.py`) — single source of truth,
   Word-safe output, trivial to re-run after content changes.
2. Use docx-mcp for **review/tracked edits/comments** on existing Word files, not for
   package creation from markdown.
3. After any docx-mcp `save_document`, diff the rels and check `repairs` in the response.
4. Open the result in Word immediately; press F9 / allow field update to populate the TOC.
